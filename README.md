# ДЗ №2 – Сбор на поездку команды

Контракт `TripFund` собирает ERC-20 на поездку. Реализованы базовый вариант и бонусное обновление V1 –> V2 с оплатой за другого участника.

## Установка и запуск

Нужны Node.js 22+ с npm и Foundry.

```sh
npm ci
forge build
forge test --force -vv
```

Все зависимости устанавливаются через `npm ci`. Версии закреплены в `package-lock.json`, версия компилятора – в `foundry.toml`.

| Компонент | Версия |
|---|---|
| Foundry | 1.8.5 |
| Solidity | 0.8.33 |
| EVM | Prague |
| OpenZeppelin Contracts | 5.6.1 |
| OpenZeppelin Foundry Upgrades | 0.4.2 |
| OpenZeppelin Upgrades Core | 1.46.0 |
| forge-std | 1.17.0 |

Для проверки обновлений в `foundry.toml` включены `ffi`, `ast`, `build_info` и вывод `storageLayout`. Тесты выполняются локально, без подключения к сети блокчейна.

## Правила сбора

- При создании задаются токен, организатор, положительная цель и будущий дедлайн. Нулевые адреса запрещены, функций изменения параметров нет.
- До дедлайна `contribute(amount)` списывает токены с вызывающего. Предварительно нужно выдать `approve`. Повторные взносы суммируются.
- Ровно в дедлайн приём взносов прекращается. До этого момента вывод и возвраты запрещены даже при достигнутой цели.
- Если `totalRaised >= goal`, организатор один раз получает всю учтённую сумму через `withdraw()`.
- Если цель не достигнута, каждый участник возвращает полный вклад через `refund()`. Повторный возврат запрещён.
- `totalRaised` после выплат не уменьшается. Прямые переводы токенов не учитываются и остаются на контракте.
- Для переводов используется SafeERC20. Учёт обновляется до внешнего вызова; ошибка перевода откатывает всю операцию. Защита от повторного входа – `ReentrancyGuardTransient`, требующий EVM с поддержкой EIP-1153.

Тестовый токен основан на OpenZeppelin ERC20, без комиссии и rebasing. События: `Contributed(payer, beneficiary, amount)`, `Refunded(contributor, amount)`, `Withdrawn(organizer, amount)`.

## Обновление V1 –> V2

V1 разворачивается через `TransparentUpgradeableProxy`. Параметры задаются вызовом `initialize` при создании прокси. Повторная инициализация прокси и прямая инициализация обеих реализаций заблокированы.

Обновление разрешено только владельцу `ProxyAdmin`. Организатор сбора и владелец `ProxyAdmin` – разные роли. V2 добавляет `contributeFor(beneficiary, amount)`: платит вызывающий, а вклад и право возврата получает ненулевой `beneficiary`.

При обновлении адрес прокси и его хранилище сохраняются. V2 наследует V1 и не меняет порядок или типы переменных. Параметры сбора, вклады, `totalRaised`, флаг выплаты и токенный баланс сохраняются. Совместимость проверяется OpenZeppelin Upgrades с V1 в качестве эталона:

```sh
npm run validate:upgrade
```

## Пример взноса

Оба вызова выполняет участник, у которого есть токены. Для V1/V2 в `fundAddress` передаётся адрес прокси.

```solidity
IERC20(tokenAddress).approve(fundAddress, 100 * 10 ** 18);
TripFundCore(fundAddress).contribute(100 * 10 ** 18);
```

Сумма указана в минимальных единицах тестового токена с 18 знаками после запятой.

Локальный пример выпуска токена, взноса, обновления и оплаты за друга:

```sh
forge script script/Demo.s.sol:Demo --force -vv
```

Результат: собрано `300 * 10**18`, из них за друга – `200 * 10**18`.

## Тесты

96 тестов проверяют параметры, повторные взносы, баланс и allowance, границу дедлайна, вывод, независимые возвраты, прямые переводы и откат при ошибке токена. Общие проверки выполняются для `TripFund`, V1 и V2. Шесть fuzz-тестов запускаются по 1 000 раз.

Отдельный сценарий проверяет взнос в V1, обновление до дедлайна с сохранением данных, обычный взнос после обновления, оплату за друга и возврат другу. Также проверены права обновления и запрет повторной инициализации.
